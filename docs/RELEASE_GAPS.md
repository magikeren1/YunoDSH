# Gaps before a complete release

2026-11-13. The user confirmed the owner-DM text reply now works. Current evidence also includes 34 passing Discord test scripts and DSH authentication/Session lifecycle smoke checks. This is a working local DM MVP, not full handover acceptance. Persona is managed directly by the user in DSH and is no longer a request for persona text in this project.

## Reliable chat release gates

1. **Recovery beyond recorded intake.** Add Gateway downtime backfill and durable outbound delivery/event-gap recovery. Existing journaled queued inputs/prepared receipts and digest exports recover within their documented boundaries, but a DSH admission receipt is not proof of a completed/delivered reply. Exercise real process termination, network interruption, lost acknowledgments and repeated Discord events while logged in.
2. **Live group/context acceptance.** Only the owner's DMs are currently enabled. Configure chosen test channels, enable the required Discord message-content setup for group observation, and verify mention/reply behavior, channel/thread isolation, simultaneous users and cross-server personal memory. Verify that normal group observation does not make per-message model requests.
3. **Live memory/digest/media acceptance.** Validate actual hourly digests with new traffic, no-traffic skips, busy background work, failure/restart and large backlogs. Check real memory attribution, source references, `/memory` and `/forget`. Test image/video attachments and temporary-file recovery, including failures and queue limits. Current mocked/offline tests do not establish live model semantics. Historical facts without evidence are not retroactively repaired.
4. **Target 1C1G qualification.** Measure full-process-tree and cgroup peak usage on the selected Debian VPS: idle, chat bursts, digest plus chat, media plus chat, and coding if included. Record CPU, memory, swap, disk and backlog growth. Tune bounded work against measurements; Windows development success is not target-host qualification.
5. **Deployment/operations.** Prepare and validate systemd supervision, restart/startup ordering, configuration/credential setup, health/readiness monitoring, backups and restore. Establish an operator workflow for blocked/full journal work and retention limits. Test clean installation, upgrade, rollback and preservation of DSH-managed persona/profile settings.
6. **Release packaging.** Make a clean checkout/install reproducible on the target OS, add CI for bridge tests and pinned DSH compatibility, document the supported dependency pair, and plan storage migration/backups. Review inherited asset/license notices and feature scope. At review the root Git repository has no initial commit or remote; no push was requested or performed. Local secrets, Session logs, generated state and portable binaries must stay out of the release source.

## Features needed for the full handover scope

7. **Explicit Flash/Flagship routing.** The bridge currently inherits DSH's chosen default or its one configured override. Add logical roles and explicit upgrades through DSH, account for Web selectModel's saved-default side effect and prepared-step boundary, and validate usage/cost reporting against the chosen routes. Concrete provider/model choices remain configuration, not guessed IDs or prices.
8. **Owner DM private assistant and coding.** Current Owner DM supports chat with the chat preset, not the requested coding workflow or dedicated private long-term fact memory. Define the previously deferred execution/authorization boundaries before enabling host tools. Preserve shared tool interfaces and prevent non-owner DMs from inheriting Owner capabilities.
9. **Topology and remaining feature assessment.** The separate-process implementation is the running baseline; the native Discord plugin comparison is still pending. Inventory PRTS, image generation, optional sandbox, followups, slang/trading and other retained modules for desired release scope, dependency cost and lighter alternatives. PRTS/image generation dependencies are not installed; Docker-dependent features are not ready. Their absence should not silently redefine the handover's requirements.

## Suggested sequence

Stabilize recovery and live group/context tests first, then qualify the target host and deployment/restore process. Model routing and Owner coding can be a later release only if the user explicitly chooses a narrower chat release; they remain requirements for the full handover scope. The unresolved Policy Layer remains a discussion item, not an architecture invented by this checklist.
